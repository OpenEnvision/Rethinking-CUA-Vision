Abstract

Computer-use agents (CUAs) built on the GUI paradigm perceive through screenshots and act through mouse and keyboard, which in principle lets them operate any software that a person can operate. Intuitively, this generality requires vision at every step, both to locate each action on the screen and to observe its result.

We find that on long-horizon tasks, GUI agents lose credit to executing actions through the screen ten times as often as to grounding and recognition. GUI agents type their programs into terminals one keystroke at a time, and 94.3% of the screenshot tokens they carry show screens they have already acted on. Generality only requires that an agent can perceive what a task depends on and change what it concerns, and neither requires vision to locate every action.

We therefore decouple perception from action and treat computer use as a multimodal coding (MM-Coding) task, in which the policy acts through programs and calls vision as a tool when it needs visual information. Across frontier models of different sizes and three long-horizon benchmarks, MM-Coding improves the average task score of GUI agents by 11.1 points with 61.7% of their input tokens and outperforms the hybrid OS-Helix harness by 6.8 points, while solving 94.5% of the tasks that GUI agents solve.

Its perception can be supplied by a small vision model that does not know the task, within 1.8 points. CUAs can be trained as code agents, with grounding developed as a capability of the perception tool.

METHOD

Act through Programs, Perceive on Demand

MM-Coding removes the two forms of coupling between perception and action with two designs. Vision becomes a tool for obtaining visual information.

COUPLING 1

Vision-dependent action

Every action is specified by a coordinate on a screenshot, so programs are typed into a terminal keystroke by keystroke and their output is read from later screenshots.

DESIGN 1

Programs as actions

The agent runs Bash or Python programs that change the system state through files, application interfaces, or synthesized mouse and keyboard events. Screen primitives become a subset of what a program can do.

COUPLING 2

Action-driven perception

Every action returns a screenshot into the context, whether or not the next decision needs it.

DESIGN 2

Perception on demand

The policy passes an image and a request to the perception tool only when a step needs visual information. Perception leaves the system state unchanged, and visual information enters the context only at the steps that request it.

action space = programs ∪ (images × requests)　　observation = program output | V(image, request)

Perception as a Replaceable Tool

The interface stays fixed and the implementation can change. Three implementations progressively remove the policy's own vision.

Conclusion

Separating when an agent looks from how it acts lets perception and action improve independently.

01

The screen limits execution

GUI agents lose credit mostly while executing actions through the screen. Most of the screenshots they carry show screens already acted on, and they turn to the terminal on their own.

02

Vision serves perception

Programs change the state of the computer directly, and vision supplies only what the screen alone shows. An agent that acts through programs calls perception as a tool when it needs it.

03

Higher scores at lower cost

MM-Coding outperforms the GUI agent on every benchmark with every policy model, with fewer input tokens and fewer model calls. A small task-blind vision model supplies its perception.

CUAs can be trained as code agents, with grounding developed as a capability of the perception tool.
